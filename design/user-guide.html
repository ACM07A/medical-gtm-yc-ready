1Setup — once

From a clone to a running console in five steps.

  1. Prerequisites. Node ≥ 22.5 (for the built-in node:sqlite) and Microsoft Edge or Google Chrome installed (the browser drives infographic rendering + partner discovery — no Chromium download). Check with node -v.
  2. Install.
    npm install            # only dependency: puppeteer-core
  3. Add a key (recommended). Copy the env file and add at least a generation key so content, proposals, and comms can be drafted. Everything else stays off until keyed.
    cp integrations/.env.example integrations/.env
# then add GEMINI_API_KEY (carries generation) and/or NVIDIA_API_KEY
  4. Build the data core.
    npm run seed           # creates + seeds data-core/medyatra.db
npm run seed-tenants   # own-brand + a demo operator (dual-mode)
npm run seed-leads     # demo patient leads for the journey
npm run comms          # the 21 WhatsApp templates + headers
  5. Start it. Leave this running, then open localhost:5173/demo — your home base.
    npm run serve          # → http://localhost:5173
TipIf a page 404s or looks stale, you changed code while the server was up — stop it (Ctrl-C) and npm run serve again.

3The surfaces — what each does & how to use it

Every route below is real data, safe to click, and human-gated.

💬
/sandbox editable

The patient-journey simulator you put in front of an operator. ▶ advance or Auto-play the conversation; take any branch from the control bar (objection, visa denied, complication, goes quiet…); edit any message → Save — which routes it back to Review, so it can't send until re-approved. White-label via the “Viewing as” switch.

🖥️
/demo

Your launchpad. Live counts of partners, contacts, content, templates, leads, tenants, and a link to every capability. Start here when showing anyone.

🗂️
/console

The operator cockpit. Partner accounts ranked by fit score (quality × low current international presence), each with a reason, a contact path, and a next action — plus the portfolio scores and a live activity feed.

✅
/studio

The daily driver. One inbox of everything awaiting approval; Approve stays disabled until the gates — regulatory · contact · consent — are green. Approving writes back: publishes a page, marks a proposal sent, releases a comms draft. Scope to one operator with ?tenant=<id>.

📄
/ (landing)

The patient-facing site: launch categories with prices and the published cost-guides. A guide appears only after it passes QA and its market is cleared by the regulatory gate.

🟢
/comms

The read-only library of all 21 approval-ready WhatsApp templates (body + header + buttons). This is what a human files with Meta. To edit them interactively, use /sandbox.

🔎
/worklist

The compliant sourcing bridge: ready-to-click Google + LinkedIn search URLs per star account, so a human confirms the named decision-maker in ~10 min — manual search, no anti-bot circumvention.

📣
/distribution

Each published page repurposed into platform-native posts (LinkedIn / IG / Reddit / WhatsApp / X). All drafts — nothing auto-posts without a platform key + POST_LIVE=1 + per-post approval.

📊

A de-identified, k-anonymised funnel across operators. Every tenant + patient identifier stripped, small cells suppressed — aggregate learning, not patient-data reuse.

🔌
/plugins

What's live (🟢) vs. one key away (⚪) — image gen, social, enrichment, WhatsApp. Add a key to .env, restart, and it flips.

4The operating loop — day to day

The engine runs one loop for content and outreach alike: generate → QA → gate → human-approve → publish/send.

Content

node --experimental-sqlite data-core/gen_content.mjs        # draft cost-guides (fills gaps)
npm run qa                                                  # English drafts that pass → 'review'
node --experimental-sqlite data-core/set_regulatory.mjs <MK> verified "counsel confirmed <date>"
node --experimental-sqlite data-core/publish_site.mjs       # 'review' + cleared market → 'published'

Distribution

FORCE=1 node --experimental-sqlite data-core/repurpose_content.mjs <N>   # first N published pages → posts

Partners & outreach

npm run partner-layer      # (re)build the fit-ranked account board
npm run worklist           # the human research worklist (/worklist)
STEALTH=1 npm run discover # named decision-makers via Google→LinkedIn (real browser)
npm run infer              # infer likely emails (INFERRED, human-gate)
npm run proposals          # tailored proposals per account (→ Studio 'review')

Patient comms & the unattended cycle

npm run comms-run          # state machine → each lead's next human-gated action
npm run loop               # one full factory cycle, fails over across providers
Human gateNone of this sends or posts on its own. The scripts draft; you approve the results in /studio with one click. That separation is the whole compliance posture.

5Dual-mode — plug in an operator's leads

The engine is its own acquisition front or the backend for an outside operator who pushes leads in. Each operator is a tenant with its own token; ingestion normalises, masks PII, dedupes, and tags the source.

curl -X POST http://localhost:5173/api/lead/ingest \
  -H "content-type: application/json" \
  -H "X-Ingest-Token: <that tenant's token>" \
  -d '{"source":"<tenant-id>","leads":[
        {"handle":"+9715xxxxxxx","country":"AE","treatment":"knee replacement","consent":true}
      ]}'

Returns a breakdown — accepted / deduped / held_no_consent / held_regulatory / rejected — and the leads flow into the same journey + Studio, isolated to that tenant. (Tokens are set by npm run seed-tenants; never commit them.)

6Going live

There is no rebuild between demo and production — it's an env file plus a few real-world approvals. Full itemised checklist in build-os/12_GO_LIVE.md.

  1. WhatsApp. Provision a Business API number, submit the 21 templates to Meta, set the tokens + POST_LIVE=1. Still human-gated per message.
  2. Enrichment / social / email. Add the respective keys — each stays double-gated (dry-run until approved).
  3. Regulatory. Replace the demo market clearances with real counsel sign-off via set_regulatory.mjs. Anything not verified is auto-gated to preview.
  4. Access. Set CONSOLE_TOKEN before exposing anything beyond localhost — it Basic-Auth-gates the console, Studio, and operator APIs; the public patient site stays open.

7The rules — built in, by design

These aren't policies you have to remember; the engine enforces them.

  • ✓Facilitator, not provider — no clinical claims, diagnoses, or outcome guarantees anywhere.
  • ✓No fabrication — prices cited or marked indicative; discovered contacts stored UNVERIFIED until a human confirms.
  • ✓Human gates on every publish, send, and commercial term. The engine drafts; a person approves.
  • ✓Tenant isolation — one operator's patient data is never reused for another. Cross-tenant learning is de-identified aggregate only.
  • ✓Privacy — individual contacts + patient PII live only in the gitignored medyatra.db and outputs/proposals/. Never commit a .db.

8Troubleshooting

The common snags and their one-line fixes.

SymptomFix
localhost won't load / a route 404sThe server is stale or not running. Stop it (Ctrl-C) and npm run serve again — code changes need a restart.
“experimental-sqlite” errorYou're on Node < 22.5. Upgrade Node.
Generation fails with 429Provider rate limit. Wait a minute and retry; batch scripts back off automatically. Keep batches small.
Landing shows no guidesContent isn't published: npm run qa → set_regulatory.mjs <MK> verified → publish_site.mjs.
/distribution is emptyRun FORCE=1 node --experimental-sqlite data-core/repurpose_content.mjs <N>.
Infographics / discovery do nothingNo local Edge/Chrome found, or it's busy. Install one; for discover, close it first (profile lock).
Approve button disabled in StudioA gate isn't green — the item needs a cleared market, a verified contact, or consent. That's intended.
